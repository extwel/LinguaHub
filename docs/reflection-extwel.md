## 1. Which pattern did you implement, and what would the code look like without it?

В процессе разработки проекта LinguaHub я реализовал паттерны Factory Method и Iterator, а также комбинацию паттернов Proxy и State.

### Factory Method

Factory Method используется для создания различных типов языковых курсов.

Абстрактный класс CourseFactory определяет общий метод createCourse(), а конкретные фабрики LanguageCourseFactory и ExamPrepCourseFactory создают соответствующие объекты.

Без Factory Method создание различных типов курсов происходило бы непосредственно в приложении с использованием операторов new и дополнительной условной логики.

Это усложнило бы добавление новых типов курсов и поддержку существующего кода.

Паттерн позволил отделить процесс создания объектов от основной бизнес-логики приложения.

В рамках M3 существующая архитектура Factory Method также позволила добавить новый тип SpeakingCourse без изменения существующих фабрик.

### Iterator

В рамках M3-02 я реализовал Iterator для последовательного обхода уроков курса.

Для этого был создан класс LessonIterator, реализующий интерфейс Iterator, а CourseProgress стал реализовывать Iterable.

LessonIterator предоставляет методы hasNext() и next().

Теперь пользовательский интерфейс может отображать уроки с помощью enhanced for без самостоятельного управления индексами коллекции.

Без Iterator обход уроков мог бы выполняться с помощью обычного цикла for и обращения к элементам списка по индексам.

Стандартный Iterator коллекции также мог решить эту задачу, однако собственная реализация позволила продемонстрировать структуру паттерна и отдельно протестировать механизм обхода.

### Combination: Proxy + State

В рамках M3-04 я реализовал совместную работу паттернов Proxy и State.

Proxy проверяет факт приобретения курса.

State определяет допустимость завершения уроков в зависимости от текущего состояния регистрации.

Для этого интерфейс EnrollmentState был дополнен методом canContinueLearning().

ActiveState разрешает выполнение уроков, а остальные состояния запрещают эту операцию.

После завершения последнего урока регистрация переходит в состояние COMPLETED.

Без такого разделения проверки приобретения курса, состояния регистрации и изменения прогресса могли бы находиться внутри одного большого метода.

Комбинация позволила разделить ответственность компонентов и сохранить понятную структуру приложения.

## 2. Where did you over-engineer first, and how did you notice?

В начале разработки проекта мы стремились использовать различные паттерны проектирования и создавать отдельные архитектурные компоненты.

Однако некоторые решения оказались избыточными для текущих требований приложения.

Наиболее показательным примером стал CheckoutFacade.

Этот класс использовался для подготовки заказа и оформления покупки, но практически все операции выполнялись через CartService.

Во время Pattern Audit мы обнаружили, что CheckoutFacade создаёт дополнительный уровень делегирования без существенной практической пользы.

Данная проблема соответствует code smell Middle Man.

В результате было принято решение удалить CheckoutFacade и сохранить прямое взаимодействие App с CartService.

После рефакторинга функциональность покупки курсов сохранилась, а архитектура стала проще.

Также были сохранены автоматизированные тесты существующих пользовательских сценариев.

Работа над проектом помогла мне понять принципы YAGNI и KISS.

Необходимо добавлять архитектурные компоненты только тогда, когда они решают конкретную проблему.

Большое количество классов и паттернов не является самостоятельным показателем качества архитектуры.

## 3. How did you verify extensibility and code quality?

Для проверки архитектуры проекта я использовал автоматизированные тесты, UML-диаграммы и анализ зависимостей между компонентами.

### Iterator testing

Для Iterator были добавлены четыре теста:

- Проверка последовательного обхода уроков.
- Проверка поведения после завершения обхода.
- Проверка обхода пустой коллекции.
- Проверка обработки null.

Эти тесты позволяют убедиться в корректной работе LessonIterator независимо от пользовательского интерфейса.

### Pattern Combination testing

Для комбинации Proxy и State были добавлены пять отдельных тестов.

Они проверяют:

- Запрет доступа к неприобретённому курсу.
- Открытие приобретённого курса в состоянии ACTIVE.
- Выполнение урока в состоянии ACTIVE.
- Переход в COMPLETED после завершения последнего урока.
- Запрет дальнейшего завершения уроков после COMPLETED.

Таким образом, была проверена не только работа отдельных паттернов, но и их совместное взаимодействие.

## 4. Which pattern would you remove if you started over? Why?

Если бы я начинал разработку LinguaHub заново, я бы не стал добавлять Facade на начальном этапе проекта.

Facade полезен, когда необходимо упростить взаимодействие клиента с несколькими сложными подсистемами.

Однако в нашем проекте CheckoutFacade в основном делегировал операции одному CartService.

Поэтому он создавал дополнительный уровень абстракции без достаточной практической пользы.

Я бы сохранил прямое взаимодействие App с CartService и добавил Facade только после появления нескольких независимых подсистем, требующих отдельной координации.

Также я бы заранее определил критерии выбора паттернов и способы проверки их реализации.

Это позволило бы уменьшить количество лишних изменений и уделить больше внимания основной функциональности приложения.

Данный опыт помог мне понять, что каждый паттерн должен соответствовать конкретным требованиям проекта.

## Teamwork

В ходе разработки проекта мы распределяли задачи между двумя участниками команды.

Каждая задача выполнялась в отдельной ветке Git.

После завершения работы создавался Pull Request, который проверял второй участник команды.

Такой подход позволил:

- Разделить ответственность участников.
- Контролировать изменения исходного кода.
- Проверять результаты работы друг друга.
- Сохранять историю разработки.
- Уменьшать вероятность возникновения конфликтов.
- Поддерживать работоспособность основной ветки main.

Для управления задачами использовались GitHub Issues и Milestones.

Итоговые этапы проекта зафиксированы релизными тегами v0.1, v0.2 и v0.3.
