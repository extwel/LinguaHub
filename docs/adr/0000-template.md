# ADR-0003: Layered Architecture for LinguaHub

- Status: accepted by ADR-0002
- Date: 2026-11-17
- Deciders: <LinguaHub Development Team>

## Context
LinguaHub — это онлайн-платформа для продажи языковых курсов. Система позволяет пользователям просматривать доступные курсы, добавлять их в корзину, применять скидки, использовать подарочные сертификаты, покупать курсы и получать сертификаты после завершения обучения.

## Options considered
1. Simple Layered Architecture
   + Pros: простота в понимании и реализации, разделяет пользовательский интерфейс, бизнес-логику и данные.
   - Cons: Может создавать тесную связь между слоями и не требует сильных границ модулей.

2. Clean Architecture
   + Pros:  поддерживает бизнес-логику независимо от фреймворков и внешних систем.
   - Cons:  может привести к появлению слишком большого количества абстракций и ненужной сложности для небольшого проекта на Java.

3. Microservices Architecture
   + Pros: самостоятельное развертывание, масштабируемость и отдельные сервисы.
   - Cons: требуется сетевая связь, координация обслуживания и дополнительная инфраструктура.

4. Modular Monolith with Hexagonal Architecture
   + Pros: четкие границы модулей, изолированная бизнес-логика, простое тестирование и гибкость.
   - Cons: требуется больше интерфейсов и тщательное управление зависимостями.

## Decision
We chose Simple Layered Architecture.

Приложение будет разделено на три основных слоя:

Layer Presentation - обрабатывает пользовательское взаимодействие через консоль.

Business Logic Layer - управление выбором курса, операциями с тележкой, расчетами скидок, покупками, регистрациями и сертификатами.

Data Access Layer - хранит и извлекает данные о курсе, пользователе, заказе и регистрации.

Каждый слой будет иметь конкретную ответственность. Layer Presentation взаимодействует с Layer Business Logic, а Layer Business Logic получает доступ к данным через Layer Data Access.

Эта архитектура обеспечивает ясную структуру, одновременно сохраняя проект простым для разработки, понимания и демонстрации.

## Consequences
Good: Простая и понятная структура проекта.

Упрощение отладки и тестирования.

Четкое разделение обязанностей.

Более быстрое внедрение.

Удобная интеграция проектных шаблонов.

Более легкое будущее развитие.

Bad / cost: Слои могут стать тесно взаимосвязанными, если обязанности не будут соблюдаться.

Бизнес-логика может стать перегруженной слишком большим количеством обязанностей.

Добавление дополнительных модулей и функций может потребовать дальнейшей реструктуризации.

Требуется дисциплина для предотвращения прямого доступа к данным с уровня презентации.
