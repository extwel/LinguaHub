
# ADR-0001: Technology Stack and Quality Assurance

## Status

Accepted — retrospective documentation.

## Date

2026-11-27

## Deciders

LinguaHub Development Team:

- Ayan (extwel)
- Aniyar (Aniyar1)

## Context

LinguaHub — учебный проект по дисциплине
Application Design Based on Patterns.

Цель проекта заключается в разработке приложения
для просмотра, приобретения и прохождения
языковых курсов с практическим использованием
паттернов проектирования.

При разработке необходимо обеспечить:

- Понятную структуру исходного кода.
- Поддержку объектно-ориентированного программирования.
- Возможность реализации паттернов проектирования.
- Автоматическое тестирование.
- Контроль архитектурных зависимостей.
- Контроль покрытия исходного кода тестами.
- Совместную разработку двух участников.
- Воспроизводимую сборку проекта.
- Документирование архитектурных решений.

Данный ADR ретроспективно фиксирует технологические
решения на основании истории разработки проекта,
конфигурационных файлов и результатов тестирования.

## Options considered

### Programming language

#### Java

Advantages:

- Поддержка объектно-ориентированного программирования.
- Статическая типизация.
- Поддержка интерфейсов и абстрактных классов.
- Удобная реализация GoF-паттернов.
- Развитые инструменты автоматического тестирования.

Disadvantages:

- Относительно большой объём исходного кода.
- Необходимость настройки Java Development Kit.

#### Python

Advantages:

- Простой синтаксис.
- Быстрая разработка приложения.
- Удобное создание прототипов.

Disadvantages:

- Динамическая типизация.
- Меньшая наглядность некоторых архитектурных
  ограничений на этапе компиляции.

#### C#

Advantages:

- Поддержка объектно-ориентированного программирования.
- Развитые средства тестирования.
- Удобная реализация паттернов.

Disadvantages:

- Потребовалось бы изменение предоставленной
  конфигурации учебного проекта.

### Build system

#### Maven

Advantages:

- Стандартная структура Java-проекта.
- Управление зависимостями через pom.xml.
- Единый жизненный цикл сборки.
- Интеграция JUnit, ArchUnit и JaCoCo.
- Удобная интеграция с GitHub Actions.

Disadvantages:

- XML-конфигурация может быть объёмной.

#### Gradle

Advantages:

- Гибкая конфигурация сборки.
- Поддержка автоматизации сложных процессов.

Disadvantages:

- Дополнительная сложность конфигурации
  для небольшого учебного проекта.

### User interface

#### Console application

Advantages:

- Простая реализация.
- Минимальное количество зависимостей.
- Удобная демонстрация бизнес-логики.
- Возможность сосредоточиться на паттернах.

Disadvantages:

- Отсутствие графического интерфейса.
- Ограниченные возможности взаимодействия
  с конечным пользователем.

#### Graphical or web application

Advantages:

- Более удобный пользовательский интерфейс.
- Возможность дальнейшего расширения продукта.

Disadvantages:

- Дополнительные библиотеки и фреймворки.
- Увеличение объёма разработки.
- Дополнительные требования к тестированию.

Перечисленные альтернативы рассматриваются
ретроспективно. История репозитория не подтверждает,
что каждая из них обсуждалась командой отдельно.

## Decision

Использовать Java 17 и Maven в качестве
основных технологий разработки.

Приложение реализовать в виде консольной программы
с многослойной архитектурой.

Использовать хранение данных в оперативной памяти
без подключения внешней базы данных.

Для разработки и контроля качества использовать
следующие инструменты:

| Technology | Version | Purpose |
|---|---|---|
| Java | 17 | Основной язык программирования |
| Maven | Build tool | Сборка и управление зависимостями |
| JUnit Jupiter | 5.10.2 | Автоматическое тестирование |
| ArchUnit | 1.2.1 | Проверка архитектурных правил |
| JaCoCo | 0.8.12 | Анализ покрытия кода |
| Maven Surefire | 3.2.5 | Запуск автоматических тестов |
| Git | Version control | Управление версиями |
| GitHub | Repository hosting | Совместная разработка |
| GitHub Actions | CI | Автоматическая проверка проекта |
| Mermaid | Documentation | UML и архитектурные диаграммы |
| Markdown | Documentation | README, ADR и Pattern Register |

Выбранные версии библиотек зафиксированы
в файле pom.xml.

## Project structure

Проект использует стандартную структуру Maven.

```text
LinguaHub/
├── .github/
│   └── workflows/
├── docs/
│   ├── adr/
│   ├── PATTERN_REGISTER.md
│   └── audit.md
├── scripts/
├── src/
│   ├── main/
│   │   └── java/
│   └── test/
│       └── java/
├── README.md
└── pom.xml
```

Исходный код приложения отделён
от автоматических тестов.

Архитектурная документация хранится
в директории docs.

## Development workflow

Совместная разработка организована
с использованием GitHub.

Приняты следующие правила:

1. Каждая задача оформляется отдельным Issue.
2. Для задачи создаётся отдельная ветка.
3. Изменения фиксируются через Git Commit.
4. Для объединения создаётся Pull Request.
5. Выполняются автоматические проверки.
6. Второй участник команды проверяет изменения.
7. После одобрения изменения объединяются с main.

Прямые коммиты в main не входят
в принятый командный процесс разработки.

Milestones используются для разделения
работы на этапы.

Release tags используются для фиксации
состояния проекта на контрольных этапах.

## Quality assurance

### JUnit

JUnit используется для проверки:

- Создания объектов курсов.
- Работы репозитория.
- Поиска курсов.
- Операций с корзиной.
- Расчёта скидок.
- Подарочных сертификатов.
- Оформления покупки.
- Уведомлений.
- Прогресса обучения.
- Выдачи сертификатов.
- Реализованных паттернов проектирования.

### ArchUnit

ArchUnit используется для автоматической проверки
архитектурных зависимостей между пакетами.

Архитектурные тесты позволяют обнаружить
нарушения разделения ответственности
между слоями приложения.

### JaCoCo

JaCoCo используется для измерения покрытия
исходного кода автоматическими тестами.

Минимальный установленный порог
покрытия строк составляет 60%.

Проверка выполняется во время
жизненного цикла Maven verify.

### GitHub Actions

GitHub Actions выполняет автоматическую
сборку и проверку проекта.

Основная команда проверки:

```bash
mvn -B verify
```

Для сборки используется Eclipse Temurin Java 17.

Дополнительно выполняется проверка
архитектурной документации через
scripts/check-deliverables.sh.

## Implementation history

### M1 — Project foundation

На начальном этапе сформирована основа проекта:

- Репозиторий GitHub.
- Конфигурация Maven.
- Структура исходного кода.
- Автоматическое тестирование.
- Архитектурные ограничения.
- Документация проекта.
- User Stories и организация командной разработки.

### M2 — Application functionality

На втором этапе реализованы основные
пользовательские сценарии:

| ID | Functionality |
|---|---|
| US-01 | Просмотр каталога курсов |
| US-02 | Поиск курсов |
| US-03 | Добавление курса в корзину |
| US-04 | Удаление курса из корзины |
| US-05 | Применение скидок |
| US-06 | Подарочные сертификаты |
| US-07 | Подтверждение покупки |
| US-08 | Покупка и регистрация на курсе |
| US-09 | Отслеживание прогресса |
| US-10 | Получение сертификата |

Для реализации функциональности
использованы паттерны:

- Factory Method.
- Strategy.
- Observer.
- State.
- Facade.

Также использован архитектурный паттерн Repository.

Результат этапа зафиксирован тегом v0.2.

### End-to-end testing

В рамках Pull Request #48 добавлен EndToEndTest.

Тест проверяет полный пользовательский сценарий
от поиска курса до получения сертификата
после завершения обучения.

Это позволило проверить совместную работу
основных компонентов системы.

### Quality check

В рамках Pull Request #51 выполнена
финальная проверка качества этапа M2.

Согласно отчёту M2-12:

| Metric | Result |
|---|---|
| Tests | 132 |
| Failures | 0 |
| Errors | 0 |
| Skipped | 0 |
| ArchUnit rules | 3 passed |
| Line coverage | 80.1% |
| Instruction coverage | 83.7% |
| Branch coverage | 73.0% |

Полученные результаты превышают
минимальный порог покрытия строк.

При использовании JDK 27 обнаружена
проблема совместимости инструментов
анализа байт-кода.

Переход на Java 17 позволил успешно
выполнить сборку проекта.

Данный результат подтверждает необходимость
использования согласованной версии Java
в локальной среде и GitHub Actions.

### Pattern Audit

После завершения основной функциональности
проведён аудит архитектуры.

В рамках Pull Request #53 удалён
избыточный паттерн Facade.

Изменения выполнены без замены
технологического стека.

После рефакторинга команда mvn clean verify
завершилась успешно.

Все установленные пороги JaCoCo выполнены.

## Consequences

### Positive

- Единый технологический стек для команды.
- Воспроизводимый процесс сборки.
- Автоматическая проверка функциональности.
- Контроль архитектурных зависимостей.
- Возможность измерять покрытие кода.
- Удобная реализация паттернов проектирования.
- Прозрачная история разработки.
- Возможность безопасного рефакторинга.
- Документирование архитектуры.

### Negative

- Приложение ограничено консольным интерфейсом.
- Данные не сохраняются после завершения программы.
- Требуется совместимость используемой версии Java
  с инструментами тестирования и анализа.
- Maven и GitHub Actions требуют поддержки
  актуальной конфигурации.
- Финальная проверка документации может завершаться
  ошибкой до выполнения всех требований проекта.

## Limitations

На текущем этапе проект не использует:

- Внешнюю базу данных.
- Реальные платёжные системы.
- Серверную инфраструктуру.
- Графический или веб-интерфейс.

Добавление данных компонентов возможно
при появлении соответствующих требований.

Согласно принципу YAGNI дополнительные
технологии не внедряются преждевременно.

Успешное прохождение Maven verify не означает,
что все финальные требования к документации
и количеству паттернов уже выполнены.
